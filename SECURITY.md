# Security

Itda controls computers remotely, so security reports are very welcome.

## Reporting a vulnerability

Please **do not open a public issue**. Use GitHub's private
[security advisory form](https://github.com/jiunbae/itda/security/advisories/new) instead. Include:

- what you found
- steps to reproduce
- the version (Settings → 정보)

You will get a reply within a week.

## Design and known limits

| Area | How it works | Limit |
|---|---|---|
| Saved credentials | Windows Credential Manager (`Itda/…`) on Windows; login Keychain (service `Itda`) on macOS. Saved passwords are not returned to the browser. | Itda uses these credentials to sign in to remote devices. Access to the local OS account and its credential vault must be trusted. Windows CLI `-p` passwords can appear in the process list and shell history; prefer a saved login. |
| Mac / VNC connections | Apple ARD login uses Diffie-Hellman and AES-128; standard VNC password authentication uses a DES challenge. SSH can wrap the connection using system OpenSSH. | ARD login does not authenticate the server's identity, and screen traffic is not encrypted by ordinary VNC. Use SSH on untrusted networks. SSH host keys are kept in `known_hosts` inside Itda's data directory; a changed key stops the connection. |
| RDP bridge (Mac app / web viewer) | Requires NLA/CredSSP (NTLM) over TLS through IronRDP; a TLS-only negotiation is refused before login credentials are sent. An existing saved server public key is checked on every route before CredSSP. LAN fallback requires a previously saved key. | First use records the key without a separate certificate trust prompt (TOFU). Certificate-chain and hostname verification are not performed. A changed key is refused; forgetting it in the desktop host menu restores first-use trust. Verify unexpected key changes independently. Windows connections opened by `mstsc` use Windows' own RDP security UI. |
| Web viewer | A 6-digit PIN creates a 12-hour HttpOnly, SameSite=Strict session cookie. Browser WebSocket and edit requests are checked against their origin. Resetting the PIN invalidates existing sessions. | A PIN holder can use saved logins to connect and can manage the address book; the PIN is not a restricted guest account. Web edits that change a connection's destination clear its saved profile credentials and detach its screen account and any file account using the inherited endpoint; an explicitly configured file host keeps its separate binding. Browser edits cannot attach another saved screen account. Approve saved-account assignments in the desktop app. |
| PIN backoff | Five failed PIN attempts from one source cause a one-minute pause for that source. A 50-failure aggregate backstop pauses new sign-ins across sources for one minute. Direct connections are counted by peer IP; loopback proxy connections may use `X-Forwarded-For`. Source bookkeeping is limited to 1,024 entries; additional sources still count toward the aggregate backstop. | A shared source or aggregate lockout can block legitimate new sign-ins; existing authenticated sessions remain usable. Trust the local proxy and its forwarded-address configuration. The backoff does not make a 6-digit PIN suitable for a public internet service. |
| Browser transport | The web listener is reachable on the configured network port. Tailscale HTTPS can provide an encrypted browser connection. | Ordinary `http://` does not protect the PIN, session cookie or screen from a network observer. Use your own trusted network or Tailscale HTTPS; never forward the web port to the internet. |
| Windows “Share this PC” | A random 8-character VNC password is checked before the optional on-screen approval prompt. Approval is enabled by default; “trust nearby devices” is off by default for new installs (settings saved by earlier versions keep their value). | “Nearby” means an IP address range, not proof of device ownership: private, loopback, link-local, IPv6 ULA and `100.64.0.0/10` addresses skip the prompt after a correct password when this option is on. Turn off **공유 → 내 기기는 묻지 않기** to require approval on those networks. A web-viewer connection to this device skips the prompt because it already passed the PIN. VNC password authentication remains weak; use a trusted network or tunnel. |
| Mac high-performance sharing | The Itda capture server listens on loopback and is reached through SSH. It needs macOS Screen Recording permission for capture and Accessibility permission for input. | It does not provide Apple's privileged login-window control. Granting permissions to a different app or executable does not prove this server has them. |
| SSH installation and configuration sharing | Requires a previously trusted SSH host key with strict checking. Selected profiles/preferences transfer over SSH; passwords and explicitly assigned account keys are separate opt-in items imported into the destination credential store/key folder. | Trust the destination OS account. Permission grants, host trust records, default SSH key folders and sharing/public-web settings are not copied. The operation can close/restart the destination app after confirmation; a login without usable credential-vault access cannot receive passwords/key passphrases. |
| View-only sharing | Itda's sharing server blocks remote keyboard/pointer input and clipboard sharing in both directions in view-only mode. | This is a sharing-server policy. For third-party VNC/RDP servers, their own permissions and the viewer's clipboard settings also apply. |
| Mac app and updates | Official Mac release bundles use Developer ID signing and Apple notarization. The app's internal gateway listens on `127.0.0.1` and authenticates app windows with a random per-launch token. Mac updates check release SHA-256 and require the expected signing team. | Notarization does not grant Screen Recording or Accessibility permission. Local processes still need the gateway token to sign in. Unsigned development builds have a different trust status. Windows releases are not Authenticode-signed; their updater checks the release SHA-256, which is not an independent publisher signature. |
| Test hooks | `ITDA_TEST_HTTP` supplies a test webview bridge; Windows also has `ITDA_TEST_SNAP` and `ITDA_DEBUG_PORT` for automation. | Leave these environment variables unset in ordinary use. Test bridges and debug listeners are for isolated developer fixtures, not shared or internet-facing sessions. |

The data directory is `%APPDATA%\Itda` on Windows and `~/Library/Application Support/Itda` on macOS. It contains profiles, settings, SSH known hosts and optional screen previews. These files and diagnostic logs may reveal device names, addresses, paths or screen contents; review them before sharing a bug report.
